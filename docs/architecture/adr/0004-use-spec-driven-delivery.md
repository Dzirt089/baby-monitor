# ADR-0004: Облегчённый Spec-Driven Development

- **Статус**: Accepted
- **Дата**: 2026-10-20
- **Решение принимает**: ведущий архитектор
- **Связанные документы**: [конституция](../../../.specify/memory/constitution.md), [AGENTS.md](../../../AGENTS.md)

## Контекст

Над проектом работают человек и несколько AI-агентов. Нужна трассируемость «требование →
решение → задача → проверка» без десятков расходящихся status-файлов. GitHub Issues не заменяют
техническую декомпозицию, а свободный чат — источник истины.

## Решение

Принят облегчённый SDD (Spec Kit-совместимый) со структурой:

- AGENTS.md — постоянные правила;
- .specify/memory/constitution.md — проверяемые принципы;
- .specify/specs/NNN-slug/{spec.md, plan.md, tasks.md, checklists/requirements.md};
- docs/product/vision.md и roadmap.md;
- docs/architecture/architecture.md и ADR;
- CHANGELOG.md — только выпущенные пользовательские изменения.

tasks.md — единственный task ledger для активной feature; стабильные ID TNNN, статусы
[ ]/[-]/[x]; задача не отмечается выполненной без фактической проверки. Порядок:
constitution → spec → clarify → plan → checklist → tasks → consistency analysis → implementation →
convergence. Чек-лист требований проверяет независимый ревьюер, а не автор.

## Рассмотренные альтернативы

| Альтернатива | Плюсы | Минусы | Почему отклонена |
|---|---|---|---|
| Только GitHub Issues | привычно для команд | нет spec/plan/ADR-трассируемости, issues дублируют tasks | слишком грубо для архитектурных решений |
| Полный GitHub Spec Kit с шаблонами | стандартизирован | требует установки глобальных инструментов | bootstrap без установки глобальных tool |
| Свободная разработка без спеков | быстрее старт | агенты расходятся в трактовке требований | противоречит конституции |

## Последствия

- Перед реализацией feature обязательны spec/plan/tasks; изменение поведения без спеки не merge.
- Документов больше, чем в «чат-разработке», но они ограничены перечисленным набором.
- roadmap.md даёт обзор milestone, tasks.md — детали активной feature.

## Проверка и критерии пересмотра

PR-шаблон требует ссылку на spec/issue и заполненные проверки. Пересмотр — при переходе на
полноценный Spec Kit tooling или изменении процесса командой (новый ADR).
