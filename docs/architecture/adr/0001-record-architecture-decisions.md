# ADR-0001: Записывать архитектурные решения в ADR

- **Статус**: Accepted
- **Дата**: 2026-10-20
- **Решение принимает**: ведущий архитектор
- **Связанные документы**: [ADR-0004](0004-use-spec-driven-delivery.md), [AGENTS.md](../../../AGENTS.md)

## Контекст

Проект разрабатывается несколькими агентами и человеком в разное время. Решения по media,
безопасности, UI-фреймворку и релизам взаимосвязаны; если они живут только в переписке,
новые участники будут повторно их обсуждать или молча нарушать.

## Решение

Каждое значимое техническое решение фиксируется отдельным ADR в docs/architecture/adr/.
ADR имеет номер, статус (Proposed, Accepted, Superseded, Rejected), дату, контекст, решение,
альтернативы, последствия и критерии пересмотра. Принятый ADR не редактируется задним числом —
изменение оформляется новым ADR, который supersedes старый.

## Рассмотренные альтернативы

| Альтернатива | Плюсы | Минусы | Почему отклонена |
|---|---|---|---|
| Только комментарии в коде/PR | минимум формальностей | история разрознена, контекст теряется | не масштабируется на несколько агентов |
| Один большой ARCHITECTURE.md | всё в одном месте | документ быстро устаревает, правки неотслеживаемы | конфликты и потеря истории решений |
| Глобальный issue tracker вместо ADR | привычно | решения теряются среди задач | задачи не заменяют решение и его последствия |

## Последствия

- Перед реализацией значимой функции проверяется наличие релевантных ADR.
- PR, меняющий архитектурное решение, обязан добавить новый ADR.
- ADR — вход для reviewer и onboarding; ссылки на ADR обязательны в docs/architecture.

## Проверка и критерии пересмотра

CODEOWNERS/reviewer проверяют наличие ADR при изменении архитектуры. Если ADR перестал
соответствовать коду — фиксируется расхождение и создаётся superseding ADR.
